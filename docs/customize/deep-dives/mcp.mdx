As AI systems get better, they're still held back by their training data and
can't access real-time information or specialized tools. The [Model Context
Protocol](https://modelcontextprotocol.io/introduction) (MCP) fixes this by
letting AI models connect with outside data sources, tools, and environments.
This allows smooth sharing of information and abilities between AI systems and
the wider digital world. This standard, created by Anthropic to bring together
prompts, context, and tool use, is key for building truly useful AI experiences
that can be set up with custom tools.

## How MCP Works in NextCLI

Currently custom tools can be configured using the Model Context
Protocol standard to unify prompts, context, and tool use.

MCP Servers can be added to your config using `mcpServers`.

<Info>MCP can only be used in the **agent** mode.</Info>

For ready-to-use configurations for popular MCP servers, see [Example MCP Servers](/customize/deep-dives/mcp-examples).

## Quick Start: How to Set Up Your First MCP Server

Below is a quick example of setting up a new MCP server for use in your config:

1. Create a folder called `.continue/mcpServers` at the top level of your workspace
2. Add a file called `playwright-mcp.yaml` to this folder
3. Write the following contents and save

```yaml title=".continue/mcpServers/playwright-mcp.yaml"
name: Playwright mcpServer
version: 0.0.1
schema: v1
mcpServers:
  - name: Browser search
    command: npx
    args:
      - "@playwright/mcp@latest"
```

Now test your MCP server by prompting the following command:

```
Open the browser and navigate Hacker News. Save the top 10 headlines in a hn.txt file.
```

The result will be a generated file called `hn.txt` in the current working directory.

## Using JSON MCP Format from Claude, Cursor, Cline, etc

<Info>
If you're coming from another tool that uses JSON MCP format configuration files (like Claude Desktop, Cursor, or Cline), you can copy those JSON config files directly into your `.continue/mcpServers/` directory (note the plural "Servers") and NextCLI will automatically pick them up.

For example, place your JSON MCP config file at `.continue/mcpServers/mcp.json` in your workspace.

</Info>

## How to Configure MCP Servers

To set up your own MCP server, read the [MCP
quickstart](https://modelcontextprotocol.io/quickstart) and then add an MCP
server block to your [config file](./configuration.md):

```yaml title="config.yaml"
# ...
mcpServers:
  - name: SQLite MCP
    command: npx
    args:
      - "-y"
      - "mcp-sqlite"
      - "/path/to/your/database.db"
# ...
```

<Note>
When creating a standalone block file in `.continue/mcpServers/`, remember to include the required metadata fields (`name`, `version`, `schema`) as shown in the Quick Start example above.
</Note>

### How to Configure MCP Server Properties

MCP components include a few additional properties specific to MCP servers.

- `name`: A display name for the MCP server.
- `type`: The type of the MCP server: `sse`, `stdio`, `streamable-http`
- `command`: The command to run to start the MCP server.
- `args`: Arguments to pass to the command.
- `env`: Secrets to be injected into the command as environment variables.

### How to Choose MCP Transport Types

MCP now supports remote server connections through HTTP-based transports, expanding beyond the traditional local stdio transport method. This enables integration with cloud-hosted MCP servers and distributed architectures.

#### How to Use Server-Sent Events Transport (`sse`)

For real-time streaming communication, use the SSE transport:

```yaml
# ...
mcpServers:
  - name: Name
    type: sse
    url: https://....
# ...
```

#### How to Use Standard Input/Output (`stdio`)

For local MCP servers that communicate via standard input and output:

```yaml
# ...
mcpServers:
  - name: Name
    type: stdio
    command: npx
    args:
      - "@modelcontextprotocol/server-sqlite"
      - "/path/to/your/database.db"
# ...
```

#### How to Use Streamable HTTP Transport

For standard HTTP-based communication with streaming capabilities:

```yaml
# ...
mcpServers:
  - name: Name
    type: streamable-http
    url: https://....
# ...
```

These remote transport options allow you to connect to MCP servers hosted on remote infrastructure, enabling more flexible deployment architectures and shared server resources across multiple clients.

For detailed information about transport mechanisms and their use cases, refer to the official MCP documentation on [transports](https://modelcontextprotocol.io/docs/concepts/transports#server-sent-events-sse).

### How to Connect to OAuth-Protected MCP Servers

Some remote (`sse` or `streamable-http`) MCP servers require OAuth sign-in. You don't need to add anything to the config for them:

```yaml
mcpServers:
  - name: Sentry
    type: streamable-http
    url: https://mcp.sentry.dev/mcp
```

In the CLI (`cn`):

- **First connection.** When the server answers with `401 Unauthorized`, `cn` opens your browser at the server's sign-in page. A server that answers with `405` and publishes OAuth metadata gets the same sign-in. The server shows as connecting in `/mcp` until you finish. If the browser does not open, `/mcp` shows the URL to visit. `cn` only opens `https` sign-in pages (or `http` on `localhost`).
- **Where credentials go.** The client registration and tokens are saved in `~/.continue/mcp-oauth.json`, readable only by your user. Tokens are refreshed automatically.
- **Callback port.** The browser redirects to `http://127.0.0.1:33418/oauth/callback`. If that port is taken, set `NEXTCLI_MCP_OAUTH_PORT` to a free port. Existing tokens keep working after a port change; a new browser sign-in registers `cn` again for the new port.
- **Headless mode (`cn -p`).** `cn` never opens a browser. Sign in once in an interactive session, or give the server an `apiKey` or an `Authorization` header in `requestOptions.headers`.
- **Signing out.** In `/mcp`, choose the server and then **Sign out (clear OAuth credentials)**.
- **Static credentials.** If a server has an `apiKey` or an `Authorization` header, `cn` uses those and skips OAuth.

`cn` handles OAuth itself. Earlier versions started `npx mcp-remote` for servers that required sign-in; `cn` no longer does, and it doesn't reuse `mcp-remote`'s saved tokens. Sign in to each such server once in an interactive session, or configure an `apiKey` or `Authorization` header.

### How to Work with Secrets in MCP Servers

With some MCP servers you will need to use API keys or other secrets. You can leverage locally stored environment secrets.

```yaml
# ...
mcpServers:
  - name: Supabase MCP
    command: npx
    args:
      - -y
      - "@supabase/mcp-server-supabase@latest"
      - --access-token
      - ${{ secrets.SUPABASE_TOKEN }}
    env:
      SUPABASE_TOKEN: ${{ secrets.SUPABASE_TOKEN }}
  - name: GitHub
    command: npx
    args:
      - "-y"
      - "@modelcontextprotocol/server-github"
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: ${{ secrets.GITHUB_PERSONAL_ACCESS_TOKEN }}
# ...
```

### How to Limit Which Tools a Server Offers

A server sends NextCLI its full tool list, and every tool on it reaches the model unless you remove it on the NextCLI side. Naming the server, or telling the model in a prompt which tools to use, does not limit what it can call. This matters most for large remote servers that you only need a few tools from.

- **IDE extensions.** In the tools menu of the input toolbar, set the tools you don't want to **Excluded**. An excluded tool is not sent to the model. See [tool policies](/ide-extensions/agent/how-to-customize#how-to-configure-tool-policies).
- **CLI (`cn`).** MCP tools default to `ask` in the TUI and to `exclude` in `cn -p`. Remove a tool with `--exclude` or an `exclude:` entry in [`~/.continue/permissions.yaml`](/cli/tool-permissions/permissions-yaml), using the name the server gives it (check names with `/mcp`). To keep only some tools of a server, list them as `owner/package:tool_name` in an [agent file](/cli/tool-permissions/agent-files); the server's other tools are excluded. Excluded tools are not offered to the model. See [default tool permissions](/cli/tool-permissions/defaults) and [flags and patterns](/cli/tool-permissions/flags-and-patterns).

These settings change only what NextCLI offers the model. The server itself still serves every tool to any client that connects. If a server publishes a narrower endpoint, such as a read-only or docs-only URL, connect to that one when you need the server itself to refuse the other tools.
