## Flags

`--allow`, `--ask` and `--exclude` take a [tool matching pattern](#tool-matching-patterns) and can be repeated:

```bash
# Allow file writes without prompting
cn --allow Write --allow Edit

# Ask before fetching a URL, which runs without asking by default
cn --ask Fetch

# Remove the shell from a session
cn --exclude Bash

# Let a headless run fetch one site, or call one MCP server's tools
cn -p "Summarize the release notes at https://docs.example.com/releases" --allow "Fetch(https://docs.example.com/*)"
cn -p "Triage the open issues" --allow "github_*"

# Let a headless run run its tests and fix the code
cn -p "Fix the failing test" --allow "Bash(npm test*)" --allow Edit

# Allow everything (headless automation you trust)
cn -p "Set up the project" --allow "*"
```

What flags do:

- **Flags come before `permissions.yaml` and the defaults.** `--allow Edit` wins over an `exclude: [Edit]` saved in `permissions.yaml`.
- **Inside the flags, excludes come first, then asks, then allows,** whatever order you write them in. `--exclude Bash --allow "Bash(git log*)"` denies `git log`: the exclude for the whole tool matches first. To narrow a tool, exclude the pattern you don't want and let the default or a broader allow handle the rest: `--allow Bash --exclude "Bash(npm install*)"`.
- **An `--allow` is the operator's opt-in and is taken as given.** `cn -p --allow Bash` runs `curl` or `npm install`; only the commands that [never run](/cli/tool-permissions/read-only-commands#never-run) are still blocked. The exception is `--readonly`, which clamps every allow (see [Plan mode](/cli/modes/plan-mode)).
- **`--ask` in a headless run means refused,** and the tool isn't offered.
- **Two flags loosen guards that no pattern can open.** `--pass-env NAME` (repeatable) gives shell commands a secret-like environment variable they don't get by default. `--allow-private-fetch` lets `Fetch` reach `localhost` and private networks, but never cloud metadata. See [secrets and private addresses](/cli/headless-mode#secrets-and-private-addresses).
- **A pattern that can't work stops `cn` at startup** with a message that names the pattern: a pattern on a tool that has no argument to match (`--allow "github_create_issue(x)"`), an unclosed one (`--allow "Write(src"`), or an empty value.

## Tool matching patterns

The same syntax is used by the flags, by `permissions.yaml` and in the messages `cn` prints:

- `Write` matches every call to the `Write` tool. `Write()` and `Write(*)` mean the same.
- `Write(**/*.ts)` matches `Write` calls whose path matches the glob.
- `github_*` matches every tool whose name starts with `github_`. `*` matches any characters and `?` one character. Names are case-sensitive.
- `*` matches every tool.

An MCP tool keeps the name its server gives it, with no server prefix, so `github_*` covers a server whose tools are called `github_create_issue` and so on, and nothing on a server that calls the same tool `create_issue`. Check the names with `/mcp` in the TUI. To allow a whole server by name, list it in an [agent file](/cli/tool-permissions/agent-files) instead.

Only these tools take a pattern. It is matched against one argument:

| Tool | Argument the pattern matches |
|------|------------------------------|
| `Bash` | the command line |
| `Read`, `Write`, `Edit`, `MultiEdit`, `Diff` | the file path |
| `List` | the directory |
| `Fetch` | the URL |
| `Search` | the search pattern, not the files searched |

### File paths

A path pattern is matched the way the tool will use the path:

- A relative pattern is relative to the working directory; an absolute pattern works too. `*` matches within one directory and `**` any number of them: `src/*` covers `src/a.ts` but not `src/x/a.ts`; `src/**/*.ts` covers both. Dotfiles match, so `Read(.env*)` covers `.env.local`.
- The path is resolved first, so `./src/a.ts` and `/path/to/project/src/a.ts` match `src/*`, and `src/../.env` doesn't.
- Symlinks are followed. An `--allow` pattern must match both the path as written and the file it points to, so `Write(src/*)` doesn't cover a symlink in `src/` that points outside it. An `--exclude` or `--ask` pattern covers the call if either path matches.
- Matching is case-sensitive, even on a file system that isn't. `Read(.env*)` doesn't match `.ENV`.

```bash
# Allow writing TypeScript files anywhere, ask for everything else
cn --allow "Write(**/*.ts)" --allow "Edit(**/*.ts)"

# Keep the agent out of a file
cn --exclude "Read(.env*)" --exclude "Read(notes/secret*)"
```

### URLs

A `Fetch(...)` pattern is a plain glob over the URL as the model wrote it. `*` matches anything, including `/`:

```bash
# Fetch from one documentation site only
cn -p "What changed in v2?" --allow "Fetch(https://docs.example.com/*)"
```

`http://` and `https://` are different strings, and a redirect to another host isn't checked against the pattern again. Prefer `Fetch(https://docs.example.com/*)` over a pattern with a bare host.

Whatever the pattern, `Fetch` refuses private and cloud metadata addresses, redirects included. `--allow "Fetch(http://localhost*)"` alone isn't enough to reach a local server; add `--allow-private-fetch`. See [secrets and private addresses](/cli/headless-mode#secrets-and-private-addresses).

### Bash commands

A `Bash(...)` pattern is matched against the **commands** in the line, not the raw text, so quoting and extra spaces don't matter: `"npm" install` and `npm  install` both match `Bash(npm install*)`.

`--allow` and `--exclude` read the same pattern differently, and each one is cautious in its own direction:

| | `--allow` | `--exclude` and `--ask` |
|---|---|---|
| Matches | one plain command, exactly as written | any command anywhere in the line |
| When in doubt | doesn't match, so the command is not allowed | matches, so the command is blocked |

#### `--allow`: one plain command only

An allow covers a line only when the whole line is a single command that matches the pattern. Anything extra (another command, a pipe, a redirect, a wrapper, a path) means it doesn't match, and the next rule decides. In a headless run that usually means refused.

With `--allow "Bash(npm test*)"`:

| Command | Allowed | Why |
|---|---|---|
| `npm test` | ✅ | matches |
| `npm test -- --watch=false` | ✅ | `*` covers the extra arguments |
| `"npm"  test` | ✅ | quotes and spaces don't matter |
| `npm tests` | ✅ | `*` is plain text matching, so `test*` also matches `tests` |
| `npm run test` | ❌ | different words |
| `npm test && npm run lint` | ❌ | two commands |
| `npm test; curl https://example.com` | ❌ | two commands |
| `npm test \| tee out.txt` | ❌ | pipe |
| `npm test > out.txt` | ❌ | redirect |
| `timeout 60 npm test` | ❌ | wrapped in another command |
| `CI=1 npm test` | ❌ | variable set in front of the command |
| `./npm test` or `/usr/bin/npm test` | ❌ | path differs from the pattern |
| `sh -c 'npm test'` | ❌ | inline shell code |

Things to know:

- **`*` doesn't stop at a word.** `Bash(ls*)` also allows `lsof`, and `Bash(python*)` also allows `python3`. To allow exactly `npm test`, with or without arguments, and nothing else, use two patterns:

  ```bash
  cn -p "Make the tests pass" --allow "Bash(npm test)" --allow "Bash(npm test *)"
  ```

- **A pattern without `*` is exact.** `Bash(git status)` allows `git status` but not `git status -s`.
- **Quoted operators are fine.** Inside quotes, `&&`, `|` or `<` is part of the argument, so `Bash(grep*)` allows `grep "<div" index.html` and `grep '&&' build.sh`.
- **Inline code is never allowed, but script files are.** `Bash(python*)` allows `python x.py`, whatever the script does, but not `python -c 'print(1)'`. Allow a script only if you trust what it contains.

#### `--exclude` and `--ask`: any command in the line

An exclude (or ask) looks inside the line and covers it if **any** command in it matches. It also ignores the command's directory, and the words in the pattern only have to appear in order, with anything in between.

With `--exclude "Bash(npm install*)"`, all of these are blocked:

| Command | How the exclude finds `npm install` |
|---|---|
| `npm install left-pad` | matches directly |
| `npm ci && npm install left-pad` | after `&&`, `;` or `\|` |
| `cat pkgs.txt \| xargs npm install` | behind `xargs` |
| `echo $(npm install left-pad)` | inside `$(...)` |
| `sh -c 'npm install left-pad'`, `bash -lc '...'`, `eval '...'` | inside a shell string |
| `bash -c'npm install left-pad'` | shell string glued to the flag |
| `find . -exec npm install {} \;` | inside `find -exec` |
| `sudo npm install -g x`, `env CI=1 npm install`, `timeout 60 npm install`, `nohup ...`, `nice ...` | behind a wrapper |
| `/usr/bin/npm install x`, `./node_modules/.bin/npm install x` | directory ignored |
| `npm -g install x`, `npm --prefix /tmp install x` | extra words in between |
| `npm \` + newline + `install x` | line split with a backslash |

Because the words only have to appear in order, an exclude also covers extra arguments even without `*`: `--exclude "Bash(git push)"` blocks `git push --force origin main` and `git -C repo push`.

These are **not** blocked by `--exclude "Bash(npm install*)"`:

| Command | Why |
|---|---|
| `npm i left-pad`, `npm add left-pad` | a different spelling. Exclude each one: `--exclude "Bash(npm i *)" --exclude "Bash(npm add*)"` |
| `python -c 'import os; os.system("npm install x")'` | inline code in another language |
| `bash install.sh` | the exclude can't see inside a script file |
| `$CMD install x` | the command is a variable |
| `echo npm install`, `git commit -m "npm install"` | `npm install` is only text here, not a command |

A line the exclude doesn't cover isn't allowed by that. It goes to the next rule, and what happens depends on the rest of your setup:

```bash
# Safe: the headless default decides the rest, and it refuses
# python -c '...', bash install.sh and $CMD
cn -p "Fix the build" --exclude "Bash(npm install*)"

# Not safe: --allow Bash runs everything the exclude misses,
# including npm i, bash install.sh and python -c '...'
cn -p "Fix the build" --allow Bash --exclude "Bash(npm install*)"
```

<Warning>
An exclude is a guardrail, not a sandbox. Combined with `--allow Bash`, it stops the obvious spellings of a command but not a script or inline code that does the same thing. To keep a headless run from doing something, allow only the commands it needs instead of allowing `Bash` and excluding what it shouldn't run.
</Warning>

#### Examples

```bash
# Headless: run the tests and edit code; any other command beyond the
# read-only defaults is refused
cn -p "Make the tests pass" --allow "Bash(npm test)" --allow "Bash(npm test *)" --allow Edit

# Interactive: run any command without asking, but ask before installing packages
cn --allow Bash --ask "Bash(npm install*)" --ask "Bash(npm i *)" --ask "Bash(npm add*)"

# Never run git push, even chained, behind sudo or inside sh -c
cn --exclude "Bash(git push)"
```
