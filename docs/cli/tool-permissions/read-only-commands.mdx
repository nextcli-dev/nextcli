In some runs, `Bash` runs only the commands that `cn`'s built-in checks approve on their own:

- `cn -p` with the default rules
- any run with `--readonly`
- `cn -p` with an agent file that lists `Bash`

The checks look only at the command text. The lists below show what they allow and what they refuse.

## Run without asking

- Listing and reading inside the workspace: `ls -la`, `cat package.json`, `head`, `tail`, `wc -l src/a.ts`, `stat`, `grep -rn TODO src`, `find . -name "*.ts"`.
- Git commands that read: `git status`, `git diff HEAD~1`, `git log --oneline`, `git show`.

## Ask, so refused when nobody can answer

- File commands: `cp`, `mv`, `mkdir`, `touch`, `tee`, and any redirect to a file (`echo x > notes.txt`).
- Build, test and lint commands: `npm`, `yarn`, `pnpm`, `make`, `cargo`, `gradle`, `mvn`, `tsc`, `jest`, `pytest`, `prettier --write`. They run code from the repository.
- Reads outside the workspace: `cat ~/.ssh/id_rsa`, `head ~/.aws/credentials`, `ls /etc`.
- Git commands that write or reach the network: `git push`, `git commit`, `git branch`, `git remote`, and `--output=` on any git command.
- Archives: `tar`, `zip`.
- Network: `curl`, `wget`, `ssh`.
- Scripts and interpreters: `bash deploy.sh`, `python x.py`, `node script.js`. Their contents aren't read.
- Inline code and variables: `python -c '...'`, `node -e '...'`, `$CMD`, `curl x | sh`, `cat x | python3`, and `$'...'` quoting, which can spell any command.
- A variable set in front of a command. It can change what the command does: `HOME=. git status` and `GIT_CONFIG_COUNT=1 ... git status` make git read a configuration that the line chooses. These variables are fine: `CI`, `NODE_ENV`, `FORCE_COLOR`, `NO_COLOR`, `TZ`, `LANG`, `LC_*` and `DEBUG`.
- `cd` on its own, which goes to the home directory, and `cd -`, which goes back to the previous directory.
- Any command the checks don't recognise.

## Never run

In any mode and whatever the rules say:

- Commands that destroy the system, a home directory or a disk: `rm -rf /`, `rm -rf ~`, `mkfs`, `find / -delete`, `wipefs -a`.

Broad deletes always need a person, even under `--allow Bash` or `--auto`. A broad delete targets a top-level directory such as `/tmp`, or a path `cn` can't resolve, such as `rm -rf $DIR`. The TUI asks; an unattended run refuses them.

A comment can't hide a command. The checks split a line into commands the way bash does, so `ls a#; rm -rf ~` is two commands, not `ls` followed by a comment, and `rm -rf ~` never runs.

<Accordion title="How the checks read #">

  `#` starts a comment only at the start of a word: at the beginning of the line, or right after an unescaped space, a tab, or one of `|&;()<>`. Anywhere else it's part of the word.

  - `a#` is a word, so `ls a#; rm -rf ~` is two commands.
  - A `#` after an escaped space (`\ `), a form feed or a non-breaking space is part of the word too.
  - A backslash at the end of a comment doesn't continue the comment onto the next line.

</Accordion>

These checks are best-effort. They read one command line, so they can't follow a `cd`, a symlink created earlier, or what a script file does. For untrusted prompts or repositories, run `cn -p` in a container, and prefer `--readonly`.
