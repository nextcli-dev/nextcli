title: "Tool Permissions"
---

Every tool has one of three permission levels:

| Permission | Behavior |
|------------|----------|
| `allow` | Runs automatically, no prompt |
| `ask` | Prompts for approval before running (TUI only) |
| `exclude` | Hidden from the agent entirely |

## Defaults

Read-only tools (`Read`, `List`, `Search`, `Diff`, `AskQuestion`, `Checklist`, `Status`, `CheckBackgroundJob`, `ReportFailure`) default to `allow`, and so do `Fetch` and `UploadArtifact` in the TUI. `AskQuestion` is a built-in read-only tool that lets the agent pause and ask for clarification before continuing. Write tools (`Edit`, `MultiEdit`, `Write`), `Bash`, `Subagent` and MCP tools default to `ask`.

[Headless mode](/cli/headless-mode) has nobody to approve a tool, so it is closed by default:

| Tool | Headless default |
|------|------------------|
| `Read`, `List`, `Search`, `Diff` and the other read-only tools | `allow` |
| `Edit`, `MultiEdit`, `Write` | `ask`, so refused |
| `Bash` | Only commands NextCLI can tell are read-only run (`ls`, `cat`, `grep`, `git status`, `git diff`, `git log`…). Everything else, including `cp`, `mv`, `tee`, `curl`, `npm install`, `npm test`, `npm run`, `make`, `cargo`, a file redirect (`> file`), a git command that writes, and a read outside the workspace (`cat ~/.ssh/id_rsa`), asks, so it is refused. |
| `Fetch`, `UploadArtifact` | `exclude`: they can send data off the machine |
| `Subagent`, MCP tools and any other tool | `exclude` |

Any `ask` with nobody present is refused. A tool that is `exclude`d, or that would always be refused, is not offered to the model. A refused call tells the model it isn't allowed in an unattended run.

To let a headless run use more, opt in with `--allow` (see below). This keeps a run that reads untrusted code, such as a pull request in CI, from running arbitrary commands or sending data out while it holds a provider key.

## Overriding with flags

Use `--allow`, `--ask`, and `--exclude` to override defaults at launch:

```bash
# Allow file writes without prompting
cn --allow Write --allow Edit

# Exclude terminal commands
cn --exclude Bash

# Let a headless run fetch URLs, or call one MCP server's tools
cn -p "Summarize this page" --allow Fetch
cn -p "Triage the issue" --allow "github_*"

# Let a headless run run its tests
cn -p "Fix the failing test" --allow "Bash(npm test*)" --allow Edit

# Allow everything (headless automation you trust)
cn -p "Set up the project" --allow "*"
```

Flags take precedence over the defaults and `permissions.yaml`. An `--allow` you write yourself is taken as given: `--allow Bash` runs any command the built-in checks don't block, not only the read-only ones. The exception is `--readonly` (see [Modes](#modes)).

## Tool matching patterns

Flags accept tool matching patterns:

- `Write` — matches any call to the `Write` tool
- `Write(*)` — same as above
- `Write(**/*.ts)` — matches `Write` calls where the primary argument matches the glob `**/*.ts`
- `github_*` — matches every tool whose name starts with `github_`

The primary argument is the file path for `Read`, `Write`, `Edit`, `MultiEdit` and `Diff`, the directory for `List`, the pattern for `Search`, the URL for `Fetch` and the command for `Bash`. Other tools take no pattern: `cn` refuses to start if one has a pattern, because a rule that never matches would leave the tool open. The same syntax works in flags and in `permissions.yaml`.

A file path pattern is matched against the path the tool will use:

- A relative pattern is relative to the working directory. `*` matches within one directory and `**` matches any number of them: `src/*` covers `src/a.ts` but not `src/x/a.ts`; `src/**/*.ts` covers both.
- The path is resolved first, so `./src/a.ts` and the absolute path match `src/*`, and `src/../.env` doesn't.
- Symlinks are followed. An `--allow` pattern must match both the path as written and the file it points to; an `--exclude` or `--ask` pattern covers the call if either matches.

```bash
# Allow writing only to TypeScript files
cn --allow "Write(**/*.ts)"

# Allow bash but not for install commands
cn --allow Bash --exclude "Bash(npm install*)"
```

A `Bash(...)` pattern is matched against each command in the line, not the raw text:

- An `--exclude` or `--ask` pattern covers the line if any command in it matches, including commands after `&&`, `;` or `|`, inside `$(...)`, `sh -c '...'` or `eval`, and behind `env`, `timeout`, `xargs`, `sudo`, `builtin`, `busybox` and similar wrappers. The command's directory is ignored (`/usr/bin/npm`), and the pattern's other words only need to appear in order, so `Bash(npm install*)` also covers `npm -g install x`. Inline code and variable commands, such as `python -c '...'` or `$CMD`, aren't covered: the next rules decide them.
- An `--allow` pattern covers only a line that is a single command, as written, with no `&&`, `;`, pipe, redirect or substitution. `Bash(npm test*)` allows `npm test` but not `npm test; curl ...`, `npm test > out.txt` or `./npm test`. It never covers inline code or a variable command, such as `python -c '...'` or `$CMD`. A script file named on the line (`bash deploy.sh`, `python x.py`) is a command like any other: its contents aren't inspected, so `Bash(python*)` allows `python x.py` whatever the script does.
- Quoting and spacing don't matter: `"npm" install` and `npm  install` match `Bash(npm install*)`.

## `permissions.yaml`

Persistent permissions are stored in `~/.continue/permissions.yaml`. This file is updated when you choose "NextCLI + don't ask again" in the TUI approval prompt. For `Bash` it remembers the command and its subcommand, such as `Bash(npm test*)` for `npm test`, so approving `npm test` doesn't approve `npm install`. A command whose first argument is an option is remembered exactly (`Bash(ls -la)`). A chained, redirected or wrapped command (`ls && npm test`, `env X=1 npm test`, `sh -c ...`) is approved once and not remembered, because a rule for it would also allow whatever runs through the wrapper.

```yaml
# ~/.continue/permissions.yaml
allow:
  - Read(*)
  - Write(**/*.ts)

ask:
  - Bash

exclude: []
```

You can edit this file directly, but it's primarily managed by the TUI. Changes take effect on the next session.

The file holds answers given in the TUI, so a headless run takes only its `exclude` rules: a personal `exclude: Bash` also removes the shell from `cn -p`, but a remembered `allow: Bash(git status*)` or `allow: Write` doesn't apply there. Opt a headless run in with `--allow` or an agent file.

## Precedence

When multiple sources define a permission for the same tool, the highest-priority source wins:

1. **Mode policies** — `--auto` and `--readonly` (see below). `--readonly` still applies your flags, but never allows writes.
2. **CLI flags** — `--allow`, `--ask`, `--exclude`
3. **`permissions.yaml`** — persistent personal settings. In headless runs, only its excludes.
4. **Defaults** — built-in policies

## Modes

Modes are a shorthand for common permission sets. Switch modes with `Shift+Tab` during a TUI session, or set them at launch:

```bash
cn --auto       # Allow all tools without prompting
cn --readonly   # Plan mode — read-only tools only, no file writes
```

| Mode | Effect |
|------|--------|
| **normal** (default) | Uses configured permissions |
| **plan** (`--readonly`) | Never writes. Reads are allowed. `Bash` and MCP tools ask in the TUI. In headless mode, `Bash`, `Fetch` and MCP tools are excluded unless `--allow` adds them. |
| **auto** (`--auto`) | Allows everything — `*: allow` |

Plan and auto modes ignore `permissions.yaml`. Auto mode ignores `--allow` and `--exclude` too; with an agent file, the file's tool list and your flags still apply.

Plan mode applies your `--allow` and `--exclude` flags, within two limits checked on every call:

- `Edit`, `MultiEdit` and `Write` are never allowed, whatever the flags say.
- `Bash` runs only commands NextCLI can tell are read-only. `--allow Bash` or `--allow "Bash(git *)"` turns the shell on, but `git push`, `cp` or `curl` still need a person, so a headless run refuses them.

So `cn -p --readonly --allow "Bash(git log*)"` adds `git log`, `--allow Fetch` adds fetching, and `--allow "github_*"` adds that server's tools. `--allow "*"` turns on every tool except the write tools, including MCP tools, which NextCLI can't check for writes. Plan mode ignores an agent file.
