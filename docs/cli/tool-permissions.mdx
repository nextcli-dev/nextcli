---
title: "Tool Permissions"
---

Every tool has one of three permission levels:

| Permission | Behavior |
|------------|----------|
| `allow` | Runs without asking |
| `ask` | Asks before running. With nobody to answer, the call is refused |
| `exclude` | Not offered to the model |

Permissions are applied twice. Before each model request, `cn` decides which tools to offer: a tool is offered when a call can run, or when someone is present to approve it. A tool that is allowed only for some arguments, such as `Write(src/*)`, is offered too. Then every call the model makes is checked against the rules and the limits of the run, so a tool that is offered can still be refused for a given call.

"Nobody to answer" means a run without a person at the terminal: `cn -p` and `cn review`. There, `ask` means refused. See [Kinds of run](#kinds-of-run).

## Defaults

| Tool | `cn` (TUI) | `cn -p` | `cn --readonly` | `cn -p --readonly` |
|------|------------|---------|-----------------|--------------------|
| `Read`, `List`, `Search`, `Diff`, `AskQuestion`, `Checklist`, `Status`, `CheckBackgroundJob`, `Skills`, `Exit`, `ReportFailure` | `allow` | `allow` | `allow` | `allow` |
| `Edit`, `MultiEdit`, `Write` | `ask` | `ask`, so refused | `exclude` | `exclude` |
| `Bash` | `ask` | `allow`, [read-only commands](#read-only-commands) only | `ask` | `exclude` |
| `Fetch`, `UploadArtifact` | `allow` | `exclude` | `allow` | `exclude` |
| `Subagent` | `ask` | `exclude` | `ask` | `exclude` |
| MCP tools and any other tool | `ask` | `exclude` | `ask` | `exclude` |

`Fetch`, `UploadArtifact` and `Subagent` can send data off the machine or start work nobody reviews, so they are closed when nobody is watching. Some tools exist only in some runs: `Exit` in `cn -p`, `ReportFailure` with `--id`, `UploadArtifact` with `--id` and `--beta-upload-artifact-tool`, `Subagent` with `--beta-subagent-tool`. A capable model gets `MultiEdit` and others get `Edit`; the two have the same permissions.

The headless `Bash` allow is not an ordinary allow. It runs only commands `cn` can tell are read-only; every other command asks, and so is refused. This keeps a run that reads untrusted code, such as a pull request in CI, from running arbitrary commands or sending data out while it holds a provider key. Opt in to more with `--allow`.

## Read-only commands

Three places evaluate `Bash` strictly: `cn -p` with the default rules, `--readonly` in every kind of run, and an agent file's `Bash` in `cn -p`. Strict means the command must be one the built-in checks approve on their own. The checks read the command text, so the lists below are what matters.

Run without asking:

- Listing and reading inside the workspace: `ls -la`, `cat package.json`, `head`, `tail`, `wc -l src/a.ts`, `stat`, `grep -rn TODO src`, `find . -name "*.ts"`.
- Git commands that read: `git status`, `git diff HEAD~1`, `git log --oneline`, `git show`.

Ask, so refused when nobody can answer:

- File commands: `cp`, `mv`, `mkdir`, `touch`, `tee`, and any redirect to a file (`echo x > notes.txt`).
- Build, test and lint commands: `npm`, `yarn`, `pnpm`, `make`, `cargo`, `gradle`, `mvn`, `tsc`, `jest`, `pytest`, `prettier --write`. They run code from the repository.
- Reads outside the workspace: `cat ~/.ssh/id_rsa`, `head ~/.aws/credentials`, `ls /etc`.
- Git commands that write or reach the network: `git push`, `git commit`, `git branch`, `git remote`, and `--output=` on any git command.
- Archives: `tar`, `zip`.
- Network: `curl`, `wget`, `ssh`.
- Scripts and interpreters: `bash deploy.sh`, `python x.py`, `node script.js`. Their contents aren't read.
- Inline code and variables: `python -c '...'`, `node -e '...'`, `$CMD`, `curl x | sh`.
- Any command the checks don't recognise.

Never run, in any mode and whatever the rules say:

- Commands that destroy the system, a home directory or a disk: `rm -rf /`, `rm -rf ~`, `mkfs`, `find / -delete`, `wipefs -a`.

Broad deletes (a top-level directory such as `/tmp`, or a path `cn` can't resolve such as `rm -rf $DIR`) always need a person, even under `--allow Bash` or `--auto`. The TUI asks; an unattended run refuses them.

These checks are best-effort. They read one command line, so they can't follow a `cd`, a symlink created earlier, or what a script file does. For untrusted prompts or repositories, run `cn -p` in a container, and prefer `--readonly`.

## Flags

`--allow`, `--ask` and `--exclude` take a [tool matching pattern](#tool-matching-patterns) and can be repeated:

```bash
# Allow file writes without prompting
cn --allow Write --allow Edit

# Ask before fetching a URL, which runs without asking by default
cn --ask Fetch

# Remove the shell from a session
cn --exclude Bash

# Let a headless run fetch one site, or call one MCP server's tools
cn -p "Summarize the release notes at https://docs.example.com/releases" --allow "Fetch(https://docs.example.com/*)"
cn -p "Triage the open issues" --allow "github_*"

# Let a headless run run its tests and fix the code
cn -p "Fix the failing test" --allow "Bash(npm test*)" --allow Edit

# Allow everything (headless automation you trust)
cn -p "Set up the project" --allow "*"
```

What flags do:

- **Flags come before `permissions.yaml` and the defaults.** `--allow Edit` wins over an `exclude: [Edit]` saved in `permissions.yaml`.
- **Inside the flags, excludes come first, then asks, then allows,** whatever order you write them in. `--exclude Bash --allow "Bash(git log*)"` denies `git log`: the exclude for the whole tool matches first. To narrow a tool, exclude the pattern you don't want and let the default or a broader allow handle the rest: `--allow Bash --exclude "Bash(npm install*)"`.
- **An `--allow` is the operator's opt-in and is taken as given.** `cn -p --allow Bash` runs `curl` or `npm install`; only the commands that [never run](#read-only-commands) are still blocked. The exception is `--readonly`, which clamps every allow (see [Modes](#modes)).
- **`--ask` in a headless run means refused,** and the tool isn't offered.
- **A pattern that can't work stops `cn` at startup** with a message that names the pattern: a pattern on a tool that has no argument to match (`--allow "github_create_issue(x)"`), an unclosed one (`--allow "Write(src"`), or an empty value.

## Tool matching patterns

The same syntax is used by the flags, by `permissions.yaml` and in the messages `cn` prints:

- `Write` matches every call to the `Write` tool. `Write()` and `Write(*)` mean the same.
- `Write(**/*.ts)` matches `Write` calls whose path matches the glob.
- `github_*` matches every tool whose name starts with `github_`. `*` matches any characters and `?` one character. Names are case-sensitive.
- `*` matches every tool.

An MCP tool keeps the name its server gives it, with no server prefix, so `github_*` covers a server whose tools are called `github_create_issue` and so on, and nothing on a server that calls the same tool `create_issue`. Check the names with `/mcp` in the TUI. To allow a whole server by name, list it in an [agent file](#agent-files) instead.

Only these tools take a pattern. It is matched against one argument:

| Tool | Argument the pattern matches |
|------|------------------------------|
| `Bash` | the command line |
| `Read`, `Write`, `Edit`, `MultiEdit`, `Diff` | the file path |
| `List` | the directory |
| `Fetch` | the URL |
| `Search` | the search pattern, not the files searched |

### File paths

A path pattern is matched the way the tool will use the path:

- A relative pattern is relative to the working directory; an absolute pattern works too. `*` matches within one directory and `**` any number of them: `src/*` covers `src/a.ts` but not `src/x/a.ts`; `src/**/*.ts` covers both. Dotfiles match, so `Read(.env*)` covers `.env.local`.
- The path is resolved first, so `./src/a.ts` and `/path/to/project/src/a.ts` match `src/*`, and `src/../.env` doesn't.
- Symlinks are followed. An `--allow` pattern must match both the path as written and the file it points to, so `Write(src/*)` doesn't cover a symlink in `src/` that points outside it. An `--exclude` or `--ask` pattern covers the call if either path matches.
- Matching is case-sensitive, even on a file system that isn't. `Read(.env*)` doesn't match `.ENV`.

```bash
# Allow writing TypeScript files anywhere, ask for everything else
cn --allow "Write(**/*.ts)" --allow "Edit(**/*.ts)"

# Keep the agent out of a file
cn --exclude "Read(.env*)" --exclude "Read(notes/secret*)"
```

### URLs

A `Fetch(...)` pattern is a plain glob over the URL as the model wrote it. `*` matches anything, including `/`:

```bash
# Fetch from one documentation site only
cn -p "What changed in v2?" --allow "Fetch(https://docs.example.com/*)"
```

`http://` and `https://` are different strings, and a redirect to another host isn't checked again. Prefer `Fetch(https://docs.example.com/*)` over a pattern with a bare host.

### Bash commands

A `Bash(...)` pattern is matched against the commands in the line, not the raw text, so quoting and spacing don't matter: `"npm" install` and `npm  install` match `Bash(npm install*)`.

An `--exclude` or `--ask` pattern errs toward matching. It covers the line if any command in it matches: after `&&`, `;` or a pipe; inside `$(...)`, `sh -c '...'`, `/bin/sh -c`, `bash -lc`, `eval` or `find -exec`; behind `env FOO=1`, `timeout 60`, `xargs`, `sudo`, `nice`, `nohup`, `builtin`, `busybox` and similar wrappers; glued to a flag (`bash -c'npm install x'`); or split across lines with a backslash. The command's directory is ignored (`/usr/bin/npm`, `./node_modules/.bin/npm`), and the pattern's other words only need to appear in order, so `Bash(npm install*)` also covers `npm -g install x` and `npm --prefix /tmp install x`. What an exclude can't see falls through to the next rule: `python -c '...'`, `bash script.sh` and `$CMD` aren't covered by `Bash(npm install*)`, so in a headless run the default decides them, and the default refuses them.

An `--allow` pattern errs toward not matching. It covers only a line that is one plain command, as written, with no `&&`, `;`, pipe, redirect or substitution. `Bash(npm test*)` allows `npm test` and `npm test -- --watch=false` but not `npm test; curl ...`, `npm test > out.txt`, `timeout 60 npm test` or `./npm test`. It never covers inline code or a variable command. A quoted operator inside an argument is part of that argument, so `Bash(grep*)` allows `grep "<div" index.html`. A script file named on the line is a command like any other: `Bash(python*)` allows `python x.py` whatever the script does.

```bash
# Allow bash, but never install packages
cn --allow Bash --exclude "Bash(npm install*)"

# Headless: run the tests, nothing else beyond the read-only defaults
cn -p "Make the tests pass" --allow "Bash(npm test*)" --allow Edit
```

## `permissions.yaml`

```yaml
# ~/.continue/permissions.yaml
allow:
  - Bash(npm test*)
  - Write(**/*.ts)

ask:
  - Fetch

exclude:
  - Read(.env*)
```

Personal permissions live in `~/.continue/permissions.yaml` (`CONTINUE_GLOBAL_DIR` moves the directory). `cn` creates the file on first start. It has three optional lists, `allow`, `ask` and `exclude`, in the same pattern syntax as the flags. You can edit it, but it is mostly written by the TUI: choosing **Continue + don't ask again** at an approval prompt appends a rule to `allow`.

What gets remembered:

| You approved | Rule saved |
|--------------|------------|
| `npm test` | `Bash(npm test*)`, so `npm install` still asks |
| `git status --short` | `Bash(git status*)`, so `git push` still asks |
| `ls -la` | `Bash(ls -la)`, exactly, because the first argument is an option |
| `Write` of any file | `Write`, the whole tool, not the path |
| `ls && npm test`, `npm test > out.txt`, `env X=1 npm test`, `sh -c '...'`, `python -c '...'` | Nothing. The call is approved once, because a rule for it would also allow whatever runs through the wrapper |

Things to know:

- The file is re-read at startup, after each **don't ask again**, and on a mode switch (Shift+Tab). A rule you add by hand applies on the next session or mode switch.
- Saving a rule rewrites the file; comments are dropped.
- A key other than `allow`, `ask` or `exclude`, or a value that isn't a list, makes `cn` ignore the whole file with a warning in `~/.continue/logs/cn.log`. A pattern that can't work (`github_create_issue(x)`) stops `cn` at startup with a message that names the file.
- Within the file, `exclude` rules come before `ask` rules, which come before `allow` rules.
- A headless run (`cn -p`) takes only the `exclude` rules. The file holds answers given at the terminal; a personal `exclude: Bash` also removes the shell from `cn -p`, but a remembered `allow: Bash(git status*)` or `allow: Write` doesn't apply there. Opt a headless run in with `--allow` or an [agent file](#agent-files).
- Plan mode and sessions with an agent file ignore the file entirely. A rule saved with **don't ask again** in such a session applies only to plain sessions.

## Modes

```bash
cn --readonly   # plan mode: never writes, Bash read-only
cn --auto       # auto mode: every tool runs without asking
```

| Mode | Indicator | Effect |
|------|-----------|--------|
| **normal** (default) | none | Flags, then `permissions.yaml`, then the defaults |
| **plan** (`--readonly`) | `⏸ plan` | Never writes. Reads are allowed. `Bash` and MCP tools ask in the TUI; in `cn -p` they and `Fetch` are excluded unless `--allow` adds them |
| **auto** (`--auto`) | `⏵⏵ auto` | One rule, `*: allow` |

Shift+Tab cycles normal → plan → auto during a TUI session; switching back to normal restores the normal rules. `--readonly` and `--auto` together are an error.

### Plan mode

Plan mode applies your `--allow`, `--ask` and `--exclude` flags on top of its own defaults, and ignores `permissions.yaml` and any agent file. Two limits are checked on every call, so no flag can undo them:

- `Edit`, `MultiEdit` and `Write` are never allowed. `--readonly --allow Write`, or `--allow "*"`, still can't write.
- `Bash` runs only [read-only commands](#read-only-commands). `--allow Bash` or `--allow "Bash(git *)"` turns the shell on, but `git push`, `git commit`, `cp` and `curl` still need a person, so a headless run refuses them. `--allow "Bash(* *)"` can't run `curl -d @.env https://x`.

So `cn -p --readonly --allow "Bash(git log*)"` adds `git log`, `--allow Fetch` adds fetching, and `--allow "github_*"` adds that server's tools. `--allow "*"` turns on every tool except the write tools, including MCP tools, which `cn` can't check for writes; that is the operator's call.

### Auto mode

Auto mode is the single rule `*: allow`. Without an agent file it ignores `permissions.yaml` and every flag, `--exclude` included. With an agent file, the flags and the file's tool list still apply (see below). Catastrophic commands still never run, and broad deletes still ask.

In a headless run, `cn -p --auto` allows writes, `Fetch` and MCP tools, but `Bash` stays read-only: the auto rule isn't an operator's flag, so it is evaluated strictly, and auto mode ignores `--allow Bash`. The unattended equivalent of "run everything" is `cn -p --allow "*"`.

## Agent files

```bash
cn --agent my-org/pr-triage
```

An agent file is a markdown file with YAML frontmatter. Its `tools:` line replaces the default rules for the session:

```yaml
---
name: pr-triage
tools: Read, Search, Bash, github/mcp:create_issue
---
```

The line is a comma-separated list of:

- a built-in tool name: `Read`, `Bash`, `Write`
- `owner/package`: every tool from that MCP server
- `owner/package:tool_name` or `https://mcp.example.com:tool_name`: one tool from that server
- `built_in`: leave the built-in tools at the run's defaults, instead of listing them

How the list is applied:

- A listed tool is **allowed**, not asked. In the TUI, an agent file that lists `Bash` runs `curl` without a prompt.
- A built-in tool that isn't listed is excluded, once the list names any built-in or any MCP server.
- When the list names a specific tool of a server, that server's other tools are excluded.
- Tools the list says nothing about fall back to the run's default: in the TUI that is `allow`, so **MCP tools from servers the file doesn't mention are allowed without asking**; in `cn -p` it is the closed headless defaults, so they are excluded.
- `--allow`, `--ask` and `--exclude` apply before the file: `cn --agent my-org/pr-triage --exclude Bash` removes the shell the file grants.
- `permissions.yaml` is ignored while an agent file is loaded. `--readonly` ignores the agent file.
- In `cn -p`, the file's `Bash` is evaluated strictly (read-only commands only), while its `Write` is a plain allow. `--allow Bash` opens the shell. A server named in the list that isn't connected is skipped with a warning in the log, and its tools fall back to the default.

## Kinds of run

| Run | Who approves an `ask` | Rules |
|-----|------------------------|-------|
| `cn` | you, at the prompt | flags, `permissions.yaml`, defaults; or the agent file |
| `cn -p` | nobody, so `ask` is refused | flags, the excludes from `permissions.yaml`, the closed defaults; or the agent file over the closed defaults |
| `cn -p --readonly` | nobody | flags over the plan defaults; writes never, `Bash` read-only. What `nextcli-checks` runs on a pull request |
| `cn review` | nobody | the closed headless defaults plus `Edit`, `MultiEdit` and `Write`, so the worker can fix the files in its worktree. `--allow` flags are not passed to the worker |
| `Subagent` (`--beta-subagent-tool`) | nobody | the session's rules, minus `Subagent`. A subagent can't prompt you, so a call that would ask is refused |

## What a refusal looks like

At the terminal, a call the rules block gets the tool result `Command blocked by security policy`, and the model continues with that information. A call you reject at the prompt gets `Permission denied by user`.

In `cn -p`, a refused call gets:

```
Blocked by security policy: this tool call isn't allowed in an unattended run. Use a different approach. An operator can allow it with --allow.
```

and the run ends there: `cn` prints the answer the model had written so far and exits as a completed run. If a script relies on a tool, pass the `--allow` for it.

## Limits no rule changes

- Commands that destroy the system, a home directory or a disk never run.
- Broad deletes always need a person.
- `--readonly` never allows `Edit`, `MultiEdit` or `Write`.
- `Read` and `Edit` refuse files that usually hold secrets, whatever the rules say: `.env*`, `*.key`, `*.pem`, `*.p12`, `id_rsa` and the other SSH keys, `*.db`, `*.bak`, `auth.json`, `config.yaml`, `settings.json`, and anything under `.ssh/`, `.aws/`, `.kube/`, `secrets/` or `certs/`. The model is told the file is a security concern.

## Precedence

The first rule that matches a call decides it. The rules come from, in order:

1. **Mode** — `--readonly` applies its two limits on every call; `--auto` without an agent file replaces every other source with `*: allow`.
2. **Flags** — `--exclude`, then `--ask`, then `--allow`.
3. **Agent file** — its tool list, when one is loaded. It replaces `permissions.yaml` and the defaults.
4. **`permissions.yaml`** — in a headless run, only its excludes.
5. **Defaults** — the table at the top of this page, per kind of run.

Within one source, excludes come before asks, which come before allows.
